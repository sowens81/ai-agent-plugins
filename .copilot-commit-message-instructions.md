# Conventional Commit Instructions

When proposing, generating, or reviewing a Git commit message, **always** follow the [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) specification. Commit messages must be compatible with automated Semantic Versioning and changelog generation (for example, semantic-release).

## Required format

```text
<type>[optional scope][!]: <short imperative summary>

[optional body]

[optional footer(s)]
```

- Use a lowercase `type` and, when present, a lowercase, hyphenated `scope`.
- Separate the type/scope from the summary with `:` (colon and one space).
- Use an imperative, present-tense summary (for example, `add`, `fix`, `remove`).
- Do not end the summary with a full stop.
- Aim for a header of 72 characters or fewer; keep it informative rather than abbreviating it beyond recognition.
- Separate the body and footer sections with blank lines. Wrap body text at approximately 72 characters when practical.
- Explain **why** the change is needed and any meaningful behaviour or compatibility implications; do not narrate every changed file.
- Output only the commit message when asked to *generate a commit message*, unless the user asks for an explanation or options.

## Allowed types and release intent

| Type | Use for | Default SemVer impact* |
| --- | --- | --- |
| `feat` | New user-facing or platform capability | MINOR |
| `fix` | Bug fix | PATCH |
| `perf` | Performance improvement | None unless configured |
| `refactor` | Internal restructuring without changed behaviour | None |
| `docs` | Documentation only | None |
| `test` | Tests only | None |
| `build` | Build system, tooling, or dependencies | None |
| `ci` | CI/CD pipeline configuration | None |
| `chore` | Routine maintenance | None |
| `style` | Formatting or whitespace without behaviour changes | None |
| `revert` | Revert a previous commit | Depends on release configuration |

*Default impacts describe common **semantic-release** conventions, not universal SemVer rules. The repository's release rules are authoritative. If `perf`, `build`, `ci`, `chore`, or another type changes released behaviour, select the type/release rules that accurately reflect the change; do not assume the type alone produces a release.

## Breaking changes (MAJOR)

- Use `!` immediately before the colon for a breaking change: `feat(api)!: remove legacy endpoint`.
- Include a `BREAKING CHANGE: <description>` footer explaining the incompatibility and, where possible, migration action. This makes the impact explicit for release notes.
- A `BREAKING CHANGE:` footer also indicates a breaking change even without `!`; prefer both for clarity.
- Breaking changes take precedence over minor or patch changes.
- Do **not** mark a change breaking merely because it is large or difficult to implement; it must break a supported contract or consumer expectation.
- Note: versions below `1.0.0` and prerelease branches may follow repository-specific release policies.

## Choosing the message

1. Inspect the actual diff or supplied change summary. Never invent work, tests, ticket IDs, or breaking changes.
2. Identify the **consumer-visible effect** (including effects on internal platform consumers).
3. Choose the most accurate type and optional scope, such as `aks`, `terraform`, `helm`, `ado`, `observability`, or `api`.
4. Decide whether the change is backwards incompatible. If uncertain, ask rather than marking it as breaking.
5. Write one concise subject describing the main change.
6. Add a body only when context, rationale, or migration guidance is useful.
7. Include issue references only when supplied or verifiably available; use the repository's established issue-reference syntax.
8. Validate the final message against these instructions before returning it.

For a commit containing multiple unrelated changes, recommend splitting it into focused commits where feasible. If a single commit is necessary, describe the dominant change and disclose any breaking impact.

## Examples

```text
feat(helm): support configurable resource requests and limits
```

```text
fix(aks): preserve ingress routing during node rotation
```

```text
ci(ado): add Terraform validation to pull request pipeline
```

```text
feat(api)!: remove legacy authentication endpoint

Remove the deprecated endpoint after clients have migrated to OAuth.

BREAKING CHANGE: Clients must use the OAuth authentication flow;
requests to the legacy endpoint will no longer succeed.
```

```text
chore(deps): update Terraform provider constraints
```

## Validation checklist

- The header matches `<type>(<scope>): <summary>` or `<type>(<scope>)!: <summary>` (scope optional).
- The type is permitted and correctly describes the change.
- The summary is clear, imperative, and free of a trailing full stop.
- The message reflects the actual change and its consumer impact.
- Any breaking change is explicitly signalled and explained.
- The anticipated release effect matches the repository's configured release rules.

Do not add emojis, conventional-commit prefixes such as `Update:`, or generic summaries such as `misc changes`.
